# 浆纱检测系统 v2 · 现场部署手册

> 版本内容：**性能与稳定性修复** + **黑纱/深色纱异常检测（新增，默认关闭）**
> 目标机器：Windows + RTX 3060 + CUDA 11.7 + cuDNN 8（已确认具备）

---

## 一、部署前须知

### 这个版本改了什么

| 变更 | 影响 |
|---|---|
| **卡顿修复（5 类根因）** | 解码线程 CPU 降约 90%；消除 Bitmap/Mat 泄漏（"越跑越卡"的根源）；修复跨线程 UI 与并发竞态 |
| **新增黑纱检测** | 深色纱缺陷检出，默认**关闭**，配置缺省时完全不影响原有流程 |
| **新增自检工具** | `--selftest` 命令行模式，装完可自查 |
| **配置脱敏** | 密码/授权码/IP 已清空，**必须重新填写**（见第三节） |

### ⚠️ 风险与验证状态（如实告知）

| 项 | 状态 |
|---|---|
| 编译 | ✅ 通过 |
| 黑纱检测算法（Python 基准） | ✅ 定位 15/16、AUROC 98.2、产线定阈召回 94%/误报 5% |
| **C# 实现与 Python 一致性** | ✅ **同后端(CPU) 80 张现场图、32 个判定帧，分数与阈值 32/32 完全相同** |
| **CPU 与 GPU 结果会有细微差别** | ⚠️ 同一批图，C#(CPU) 与 Python(GPU) 有 6/32 帧不同（如 Cam2 阈值 47.82↔44.23、某帧分数 8↔6）。这是 Transformer 前向的浮点差异在 P99 边界翻动了个别 patch，**两边都不算错**；但意味着**基准里那组 94%召回/5%误报是 CPU 上测的，开 GPU 后会略有偏移** |
| **卡顿修复的实际效果** | ⚠️ **未在真实产线验证** — 属代码层面分析与修复 |
| **黑纱检测在产线的表现** | ⚠️ **未在真实产线验证** — 基准只有 16 个缺陷样本 |
| CUDA 11.7 跑 onnxruntime(CUDA 11.8 编译) | ⚠️ **未在目标机实测**，代码已做失败自动回退 CPU |

**因此强烈建议按第五节的分阶段上线，而不是直接替换现役版本。**

## 二、安装

### 1. 拷贝

把整个 `部署包_YarnDetectionSys_v2` 目录拷到工厂机器，**建议放在现役版本旁边**（如 `D:\YarnDetection_v2\`），**不要覆盖现役目录**，以便随时回滚。

### 2. 不需要额外安装

| 依赖 | 状态 |
|---|---|
| .NET Framework 4.7.2 | Win10/11 系统自带 |
| CUDA 11.7 / cuDNN 8 | ✅ 目标机已有 |
| 海康 SDK / OpenCV / SQLite / S7 | 随包携带 |
| onnxruntime（含 CUDA 后端） | 随包携带 |
| VC++ 2015-2022 x64 运行库 | 现役系统在跑，说明已有；若报错则补装 |

> ⚠️ **内存要求：开启黑纱检测后 6 路共需约 6 GB**（实测峰值工作集 5.76 GB）。
> 每路相机要缓存 8 帧参考特征，单帧 171 MB。装之前先确认机器内存 ≥16 GB；
> 若只有 8 GB，请在 `启用相机` 里只填 2-3 路（每减 1 路省约 1 GB）。

## 三、配置（必做）

> ### 🚩 最省事的路线（推荐，30 秒搞定第 1、2 步）
> 直接把**现役版本目录里的 `System.ParamConfig.xml` 整个拷过来覆盖**，再照第 3 步补上黑纱节点即可。
> 现役文件里已经有正确的密码、授权码、相机 IP、PLC IP，**不需要重新生成任何东西**。
> 授权密钥（第 1 步）仍需设置——因为程序要用它去校验那份授权码。

### 1. 授权密钥 ≠ UUID（两个不同的东西，别混）

| 名词 | 是什么 | 谁生成 | 放哪 |
|---|---|---|---|
| **主板 UUID** | 这台电脑的硬件唯一编号 | 程序自动用 WMI 读（`Win32_ComputerSystemProduct`），你不用管 | 不落盘 |
| **授权码** | UUID 用 AES 加密后的密文 | 在"参数设置"窗口里由程序生成 | `System.ParamConfig.xml` 的 `<DVRIPConfig>` |
| **AES 密钥/IV** | 加解密用的那把"锁" | 原厂固定值（原来硬编码在源码里） | 环境变量或 exe.config |

程序启动时做的判断只有一句：`AES加密(本机UUID) == <DVRIPConfig>` → 相等才启动检测。

**为什么要改**：原来密钥硬编码在源码里，源码一上传 GitHub 授权就等于失效，所以挪到外部。**值还是你们原来那个**，二选一填：

**方式 A — 系统环境变量**（推荐）
```
YARN_LICENSE_KEY = <原16字节密钥>
YARN_LICENSE_IV  = <原16字节IV>
```

**方式 B — `YarnDectionSys.exe.config` 的 appSettings**
```xml
<appSettings>
  <add key="LicenseKey" value="原16字节密钥" />
  <add key="LicenseIV"  value="原16字节IV" />
</appSettings>
```

> ⚠️ 密钥必须和当初生成 `<DVRIPConfig>` 时用的完全一致，否则拷过来的授权码校验不过。

### 2. 设备与网络（已脱敏，需填回现场值）

**做法一（推荐）**：拷现役 XML 覆盖，见上面的🚩。

**做法二**：手工填。授权失败时程序**仍会打开窗口**（左上角显示 `System Parama Error!`，只是不启动相机），可以正常进"参数设置"窗口填写：

| 界面字段 | 填什么 |
|---|---|
| 设备密码 | 现场摄像机密码 |
| **授权码**（掩码框） | **填这台电脑的主板 UUID 明文**——程序保存时会自动加密写进 `<DVRIPConfig>`，不用自己算 |
| 相机 IP ×6 | 现场值 |
| PLC IP | 现场值 |

查本机 UUID：
```bash
wmic csproduct get uuid
```

对应的 XML 节点（如果要直接改文件）：
```xml
<DVRUserName>admin</DVRUserName>
<DVRPassword>现场密码</DVRPassword>
<DVRIPConfig>密文授权码(勿手填明文)</DVRIPConfig>
...
<CameraIdx id="1"><CameraIP>现场相机IP</CameraIP></CameraIdx>   ← 6 路都要改
<PLCIP>现场PLC IP</PLCIP>
```

### 3. 黑纱检测开关（界面上有，也可改 XML）

**界面**：主界面 →「参数设置」→ 右侧「**黑纱/深色纱检测**」分组：

| 控件 | 说明 | 现场建议 |
|---|---|---|
| 黑纱检测 | 总开关 开/关 | 第一阶段 **关** |
| GPU 加速 | 开=CUDA，关=CPU | 有 RTX3060 → **开** |
| 轮询间隔(ms) | 每路相机多久跑一次 | 10000 |
| 启用相机(1-6) | 逗号分隔，如 `1,3,5` | `1,2,3,4,5,6` |

改完点保存，**重启程序生效**。

> ⚠️ 必须处于「**运行模式**」。「调试模式」只做画面预览，不加载任何模型、不起检测循环，黑纱检测同样不工作。

**轮询间隔怎么定**（每个 tick 只处理一路相机，轮着来）：

单路复访周期 = 间隔 × 启用相机数；冷启动要攒 8 帧才开始判定，即 8 × 间隔 × 相机数。

**单帧耗时是实测值**（3200×1800 现场原图，7 个 tile）：

| 后端 | ONNX 推理 | 其余(预处理+归一化+余弦) | 单帧合计 |
|---|---|---|---|
| **GPU**（RTX4060 Laptop） | 368 ms | 45 ms | **~0.4 s** |
| CPU | 4743 ms | 45 ms | ~5 s |

非推理部分已做 SIMD + 并行优化，占比不到 10%，**所以 CUDA 有没有真挂上直接决定 10 倍差距**——务必用 `--selftest` 看「实际后端」那一行。

| 场景 | 建议间隔 | 单路复访 | warm-up |
|---|---|---|---|
| **GPU 6 路** | `1500` | 9 秒 | 1.2 分钟 |
| GPU 6 路（保守，给白纱链路留余量） | `3000` | 18 秒 | 2.4 分钟 |
| CPU 6 路 | `6000` | 36 秒 | 4.8 分钟 |

- **下限**：间隔必须大于单帧耗时，否则 tick 重入被直接丢弃（不报错，白跑）。
- **别设太小的另一个理由**：8 帧参考窗跨的时间也跟着变短，**持续性缺陷更容易被当成常态吸收**（见第七节局限 1）。GPU 下 1500ms 的参考窗只有 72 秒，缺陷持续超过这个时长就会被吸收；要兼顾及时性和参考窗长度，`3000` 是更稳的起点。
- 停机会自动重置参考缓冲，开机后重新 warm-up。

对应 XML（老配置文件没有这些节点也能正常打开，缺省=关闭）：
```xml
<BlackYarnDetect>false</BlackYarnDetect>              <!-- 第一阶段保持 false -->
<BlackYarnModelPath>testdll/dinov2_vitb14_l8_448x588.onnx</BlackYarnModelPath>
<BlackYarnIntervalMs>10000</BlackYarnIntervalMs>      <!-- 每路轮询间隔 -->
<BlackYarnUseCuda>true</BlackYarnUseCuda>             <!-- 有RTX3060,开 -->
<BlackYarnCameras>1,2,3,4,5,6</BlackYarnCameras>
```

## 四、装完自检

打开命令提示符，切到程序目录：

```bash
YarnDectionSys.exe --selftest "D:\某个黑纱图片目录" --cuda
```

### 预期输出

```
========== 黑纱检测自检 ==========
模型大小 : 330 MB
  BlackYarn: CUDA EP 已启用
模型加载耗时: 850 ms
实际后端 : CUDA (GPU)               ← 关键看这一行
待处理 13 张
  BlackYarn: 自校准完成 阈值=19 (中位6)
---------- 自检结果 ----------
处理帧数   : 13（进入判定 5，warm-up 8）
报警帧数   : 0
单帧平均耗时: 420 ms
  分段(每帧均值): 预处理 16 ms | ONNX推理 368 ms | 归一化 11 ms | 余弦比对 18 ms
```

### 判读

| 现象 | 含义 |
|---|---|
| `实际后端 : CUDA (GPU)` + 单帧 ~0.4 秒 | ✅ GPU 正常 |
| `实际后端 : CPU` + 单帧 ~5 秒 | ⚠️ CUDA 依赖有问题，功能仍可用但慢 10 倍；见故障排查 |
| 分段里 `ONNX推理` 占 90% 以上 | 正常。其余部分已优化到 45 ms 量级 |
| `找不到模型文件` | onnx 没放进 `testdll/` |
| `模型加载异常` | 缺 onnxruntime.dll 或 VC++ 运行库 |
| 正常黑纱目录上报警数很少（0-1） | ✅ 阈值自校准正常 |

## 五、分阶段上线（重要）

新版改动了取流、内存管理等核心路径，虽已验证一致性，但**未在真实产线跑过**。

| 阶段 | 做什么 | 观察什么 | 时长 |
|---|---|---|---|
| **1** | 并列安装，黑纱检测**关闭**，只跑原有功能 | 界面是否变流畅；任务管理器看**内存曲线是否还持续上涨**；原有 KC/人手检测是否正常 | 1-2 个班次 |
| **2** | 用 `--selftest` 确认 GPU 可用 | 见第四节判读 | 10 分钟 |
| **3** | 开 `BlackYarnDetect=true` | 黑纱报警是否合理；**误报率**（对照 `ErrBlack/` 目录存图人工看） | 1-2 天 |
| **4** | 稳定后替换现役版本 | — | — |

**任何阶段出问题 → 直接切回现役目录的 exe，零成本回滚**（配置文件与数据库都是独立的）。

## 五之二、日志与存图去哪找

| 位置 | 内容 | 谁写 |
|---|---|---|
| `<FilePath>/Err/camreaN/` | **白纱**拥纱故障原图 | 原有流程，未改动 |
| `<FilePath>/Err1/`、`Err2/camreaN/` | 原有的开机图 / 人手检测图 | 原有流程，未改动 |
| **`<FilePath>/ErrBlack/camreaN/`** | **黑纱**异常原图，文件名 `black_年-月-日-时-分-秒-毫秒.jpg`，已画红框标出位置 | 新增，与白纱完全隔离 |
| `YarnDectionSysLog.log` | 文本流水日志，黑纱行形如 `camrea3 黑纱异常 score=37` | 共用 |
| `System.DataBase.db` → `Logs` 表 | 结构化日志。黑纱记为 `LogType=VisionError, Event='黑纱异常'`；白纱是 `Event='拥纱故障'`，靠 Event 字段区分 | 共用 |
| 主界面「系统日志」窗口 | 上面这张表的查询界面，可按类型/时间筛 | 共用 |

> ⚠️ `Err/`、`Err1/`、`Err2/` 在停机满一定时长后会被**自动清空**（原有逻辑）。
> **`ErrBlack/` 不参与自动清理** —— 现场评估误报率要靠这些原图。请定期人工清理，别让它无限增长。

导出某天的黑纱记录：

```bash
sqlite3 System.DataBase.db "SELECT LogTime,CameraID,Confidence,FaultCenterX,FaultCenterY FROM Logs WHERE Event='黑纱异常' ORDER BY LogTime;"
```

## 六、故障排查

| 现象 | 排查 |
|---|---|
| 程序启动即退出 | 授权密钥/授权码没配对，见第三节第 1 项 |
| CUDA 回退到 CPU | ① 确认 `where cudart64_110.dll` 和 `where cudnn64_8.dll` 都能找到；② 确认 `onnxruntime_providers_cuda.dll` 在 exe 同级；③ 仍不行可先用 CPU 跑（把 `BlackYarnIntervalMs` 调大到 30000） |
| 黑纱检测无任何输出 | 缓冲需累积 ≥8 帧才开始判定；6 路轮询下约需 8×6×轮询间隔 |
| 黑纱误报偏多 | 调大 `BlackYarnIntervalMs`；或临时关闭该功能不影响原有检测 |
| 相机取流失败 | 与本次改动无关，按现役版本的排查流程处理 |

## 七、已知局限（供判断报警可信度）

1. **持续性缺陷可能漏检** — 算法用"该机位历史帧"作参考，缺陷若长期存在会逐渐被当作常态。这是该类方法的结构性特点，已有改进方案（长短期双参考库）待实施。
2. **仅 16 个缺陷样本验证** — 统计力有限，现场表现可能与基准有出入。
3. **首次运行需 warm-up** — 每路相机累积 8 帧后才开始判定。
4. **换纱批次后建议重启** — 场景整体变化会使历史参考失效（程序在检测到停机时会自动重置参考缓冲）。
