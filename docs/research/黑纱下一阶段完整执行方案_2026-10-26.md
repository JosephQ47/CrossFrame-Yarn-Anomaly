# 黑纱下一阶段完整执行方案

**2026-10-28 更新：**本文件为初版。已完成的数据审计及 C# 生产口径核对写入《黑纱下一轮实验与落地执行方案_2026-10-28.md》；后续执行以该新版为准，尤其要区分 C# 8 帧缓冲与 Python 默认 16 帧缓冲。

日期：2026-10-26。目标是检验“冻结 DINOv2 特征 + 人工缺陷监督头”能否在**同一参考协议、同一报警口径、同一相机时间流**下比现役 M0 更可靠，同时把人手入侵造成的拒判计入结果。执行时按本方案连续推进已具备条件的工作；数据门槛未满足的项目明确停在对应门槛，不用同一故障的重复帧伪装独立测试。

## 一、现在已经确定的选择

| 项目 | 固定安排 | 原因 |
|---|---|---|
| 生产基线 | 保留当前 M0（DINOv2 最后 8 层、同位置参考、P99 连通域评分，现有相机校准和人手门控） | 现有 M4/YOLO 不能证明优于 M0；M0 的历史结果不重跑训练 |
| 研究候选 | 只保留 M4 小 CNN 为首个影子模型；YOLO＋DINO 只做候选排序失败诊断，不再并行扩展新头 | M4 的 Cam3 定位已命中，首要瓶颈是阈值迁移；YOLO 正确候选曾排 15/23 |
| 训练材料 | 七月 69 张（16 阳性、53 正常）作为开发批，按相机与时间做内部分析；不把 16 张当 16 次独立故障 | 阳性全来自同一故障 |
| 锁定材料 | F2 69 张保持盲法判读，不参与训练、选头、阈值或参考池；只有取得该事件之前同状态正常历史后，才可用于因果 DINO 评估 | F2 无确认缺陷标签，每事件每机位仅 2–3 张，达不到 8 帧预热 |
| 主评价对象 | 图级报警、报警且点命中、正常误报、拒判/遮挡覆盖、每相机分布；有连续观测时长才报误报/小时 | 单独点命中或 AUROC 会掩盖错误报警与缺失覆盖 |

**不要把两种实验混成一张提升表。** 现有 M0/M4 六折均用同相机批内留一参考，属于回顾性算法开发。产线算法只用过去帧，且要先满足 8 帧预热。旧 M4 权重也是用留一参考训练的；直接把它接到因果滚动参考上，输入分布可能变化。因此先做 M4 输入与模型输出一致性检查，再做影子回放，不能把旧六折成绩当产线成绩。

| 实验编号 | 一次只改变的因素 | 可用数据与当前状态 | 能回答的问题 |
|---|---|---|---|
| E0 | 既有 M0 对既有 M4，统一六折回顾性参考 | 七月批，已完成 | 监督头是否在同事件内部学到定位；不能证明新故障收益 |
| E1 | E0 归档分数叠加现役人手门控 | 七月批，下面已核算 | 减少哪些误报、拒判哪些缺陷；不是在线性能 |
| E2 | M0 固定、仅改变正常帧校准规则 | 需要故障前同状态正常历史，当前未就绪 | 跨相机阈值是否为主瓶颈 |
| E3 | 同一因果参考、同一门控和阈值规则，M0 对 M4 影子输出 | 需先实现 M4 因果输入并达到 E2 数据门槛 | 学习头在真实时间流上是否有配对收益 |
| E4 | E3 固定后换成独立故障事件 | 等待自然发生的新事件 | 是否可以考虑替换生产基线 |

## 二、已完成的立即执行项：人手门控收益与代价

`tools/audit_black_hand_gate_tradeoff.py` 将七月 69 张归档 M0/M4 分数、人工人手标注、产线 `DetectPerson.dll` 输出和每相机两帧恢复状态机逐帧对齐；结果见 `data/black_hand_gate_tradeoff_2026-10-26.json`。这 69 张上 DLL 与人工人手标注一致：4 张人手帧，另有 4 张第一恢复帧，共 8 张不能判纱线，实际可判 61 张。

| 归档分数的事后门控核算 | M0 | M4 |
|---|---:|---:|
| 未门控：16 张缺陷中的报警 / 53 张正常中的误报 | 14/16；7/53 | 13/16；7/53 |
| 门控后：16 张缺陷中的报警 / 53 张正常中的误报 | 13/16；4/53 | 13/16；4/53 |
| 门控后可判帧 | 15 张缺陷、46 张正常 | 同左 |

其中 `DI2_Cam3_2026-07-18_10-14-15-409` **同时有人手和真实黑纱**。门控会挡掉 M0 在该帧的报警；该报警原本定位错误，但仍说明不能只报“误报下降”而隐去一张缺陷拒判。M4 该帧原已低于阈值，门控后总报警数不变，覆盖却仍损失一张。两个模型各有 3 个正常误报被门控或恢复状态挡掉。本表是**对既有分数做事后拒判核算**，没有重新建立参考池，不代表真实在线门控回放后的准确率。

## 三、连续执行流程与产出

### 阶段 A：冻结数据与评估协议（现有材料即可完成）

1. 用现有 SHA 清单确认 `black_fabric` 与现场副本只计一次；七月批标明 `development/single_fault_event`，F2 标明 `blind_holdout`。每帧清单至少含 SHA-256、源图、相机、准确时间、故障事件、运行状态/速度、缺陷框/轮廓、手部标签及标签来源。未知字段留空，不从模型输出推测真值。
2. 把人工人手标签和 DLL 预测分别保留；评估时既报理想真值门控上界，也报真实 DLL 门控结果。人手与缺陷同帧必须成为单独类别。
3. 冻结 M0/M4 权重、预处理、分数与定位规则以及阈值算法；记录 Git commit、模型文件哈希、Python/CUDA/ONNX 版本。此后任何更改产生新实验编号，不覆盖原结果。

**验收：**清单去重后 69 张、16 张阳性、53 张正常；F2 不在任何训练/调阈输入中；所有已评估图可以追溯源图、人工框和模型版本。既有 `tools/audit_causal_reference_readiness.py`、`tools/audit_black_failure_modes.py` 可复核这些前提。

### 阶段 B：同批内部机制验证（可立即继续，但只称开发诊断）

1. 在相同的七月留相机输出上，分解“候选不存在 / 候选存在但排序错 / 定位正确但分数未越阈 / 人手门控拒判 / 正常图报警”，逐相机列原图和分数。已完成 Cam3、Cam5 关键帧，后续补齐其余四台即可，不重新训练 M0。
2. 对 M4 做**校准可行性诊断**：绘制每折正常和缺陷分数分布，比较 Cam4→Cam3 与 Cam6→Cam5 的阈值漂移。测试相机正常标签只作事后分布解释，不反向设阈后宣称新成绩。
3. 跑固定参数的人手方案核算：无门控、现役硬门控、可选外观掩膜分别报拒判、误报、缺陷报警和定位。掩膜与硬门控的在线版本必须重算参考与特征；不能只用上表的事后核算替代。

**阶段 B 的结论上限：**确定下一轮工程改动优先级，不给“对新黑纱提升 X%”或独立缺陷召回。

### 阶段 C：准备可做因果回放的正常历史（当前数据门槛）

1. 从现有现场录像/采集日志优先找每相机、每运行状态、**故障之前**的连续正常原图；保留原始时间、速度、启停/换批与手部事件。禁止把故障之后的正常图或不同速度的 F2 事件倒灌到参考池。若本地没有这些原始连续帧，直接列缺口，不合成或跨状态凑数。
2. 每相机每状态先满足 **8 张**已确认正常帧作预热；内部试运行至少另留 **40 张正常帧校准阈值、60 张更晚的正常帧盲测**。这是启动门槛，不是充分的统计保证；正式比较目标扩大到每段至少 100 张并覆盖不同班次。8 张是算法可启动门槛，绝不是足以稳定估计低误报阈值的样本量。时间相邻图相关，报告有效观测时长和事件数，不把 100 张当 100 次独立实验。
3. 先固定时间切分和标签：前段正常帧供参考与阈值，后段正常帧只做盲测；缺陷帧若发生在预热之前，必须记作 `NOT_READY`，不得从召回分母中悄悄删掉。F2 盲判使用已有 `data/f2_blind_review_69_template.csv`，标签锁定后才允许查看对应模型输出。

**可启动条件：**相机、时间、状态和正常来源可以核实，且每个被评估查询帧有足够的过去同状态正常参考。当前七月阳性 0/16 就绪，F2 0/69 就绪，所以这一步的缺口不能通过多跑模型解决。

### 阶段 D：固定模型的顺序影子回放（满足 C 后自动执行）

1. 以现役 M0 为对照，严格按时间逐相机回放；参考仅来自过去已确认正常或按预先冻结规则准入的帧。E2 在同一组 M0 分数上预先比较现役 `median + 3.5×MAD` 与每相机正常校准段 P95，两套阈值都在盲测前冻结；不看盲测结果再挑其中的好值。当前 Python 部署脚本已实现滚动参考，但要记录每帧参考 ID、参考数量、运行状态、阈值来源、门控状态、分数和框，才能审计泄漏及状态变化。
2. M4 使用同一帧、同一历史参考集合构造 `F,R,|F-R|,cos` 输入；先完成原 PyTorch 权重与影子推理实现的特征/概率一致性检查。若换参考后分数失校准，只在**预先划出的正常校准段**拟合每相机阈值，固定规则后才碰盲测段。当前旧 M4 六折阈值不能移植。
3. 报 M0 与 M4 在同一可判帧上的配对差值，同时报全流结果：`NOT_READY`、`HAND_INTRUSION`、`RECOVERING`、缺陷漏报、误报和错误定位的数量。硬门控与外观掩膜分开跑；既报有手区域，也报同帧缺陷是否被遮挡。

**验收：**无未来参考、无跨运行状态参考、F2 未用于训练/调阈；每个报警能追溯图像、参考、门控、阈值和模型版本。至少保留一段连续现场影子日志用于误报/小时与延迟统计；离散七月/F2 抽样图不计算每小时误报。

### 阶段 E：独立故障验证与上线决策（等待新事件自然出现）

不要求今晚采到新黑纱。未来出现新的黑纱事件时，保留故障前预热、故障期间及恢复后的**连续原图**，整次事件封存后再评价。先观察至少 2 次与七月不同的独立故障，只作为迁移预检；正式替换 M0 还需更多事件及各相机/状态正常连续运行证据，给出分事件结果和 Wilson 95% 区间。只有 M4 在相同可判集合上提高“报警且定位正确”，且全流缺陷漏报、正常误报和拒判覆盖不劣于 M0，才进入 C#／ONNX 集成。任何一次因人手门控漏掉的同帧真实缺陷必须单列，不得改记正常。

若证据仍不足，继续让 M4 影子运行，生产保持 M0。M4 真正过关后再做 PyTorch/ONNX/C# 数值对齐、六路吞吐、报警存图与状态日志验收；不根据这 16 张开发阳性单独决定切换生产模型。

## 四、下一次自动推进时的优先顺序

1. 补齐阶段 B 的六相机逐帧失败分类、归档证据图，并用已有标注复核手部同帧缺陷；本次已先完成门控核算。
2. 在本机现有原始采集目录和日志中按事件、相机、时间搜寻阶段 C 所需的**故障前同状态连续正常帧**，生成可用/缺口表。若不存在就停止因果召回实验，继续完成不依赖它的标注和影子推理准备。
3. 准备 M4 因果特征提取与只读影子回放，先做张量/权重数值一致性，随后等待正常历史达到门槛再正式评估。

上述顺序是执行安排，不需每走一步重新选择算法。唯一不能自行补出的证据是原始采集历史、人工盲判真值及未来独立故障；缺失时如实标记，不用旧事件重复调参填空。
